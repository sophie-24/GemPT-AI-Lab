# AI Agent 면접 개념 학습서

한글과컴퓨터 AI Agent 팀 면접 준비용 개념 노트입니다. 각 장은 정의 암기보다 **왜 필요한지, 어떤 구조로 동작하는지, 어떤 실패가 있는지, 내 프로젝트에서 어떻게 설명할지**에 초점을 둡니다. 페이지 분량은 문서 글꼴과 여백에 따라 달라지므로, 여기서는 각 주제를 한 단원으로 독립 학습할 수 있도록 충분히 풀어 설명합니다.

## 1. AI Agent란 무엇인가

### 정의와 구성 요소

LLM 애플리케이션은 넓게 보면 모델을 호출하는 모든 프로그램을 포함하지만, AI Agent는 모델이 사용자 요청을 해석한 다음 **어떤 행동을 할지 선택하고, 도구를 사용하고, 그 결과를 바탕으로 다음 행동을 결정하는 실행 시스템**을 뜻합니다. 따라서 Agent는 모델 그 자체가 아닙니다. 모델은 언어 이해와 생성, 다음 행동 제안의 일부를 담당하고, 애플리케이션은 상태, 권한, 도구 실행, 재시도, 종료를 관리합니다.

일반적인 Agent 실행을 구성하는 요소는 다음과 같습니다.

1. **목표와 입력:** 사용자의 요청, 파일, 대화 문맥 등입니다.
2. **상태:** 현재까지 알아낸 사실, 아직 해야 할 작업, 도구 결과, 오류입니다.
3. **정책 또는 오케스트레이터:** 허용된 다음 단계, 횟수 제한, 승인 규칙을 결정합니다.
4. **모델:** 요청을 분석하고 답하거나 도구 호출을 제안합니다.
5. **도구:** 검색, 계산, DB 조회, 외부 API 등 실제 작업을 수행합니다.
6. **평가와 종료:** 목표가 충족됐는지, 불확실한지, 실패했는지 판정합니다.

예를 들어 GemPT Solver가 `21 / 3` 계산 도구를 요청했다고 해서 계산이 즉시 실행되는 것은 아닙니다. Flask가 도구 이름과 인자를 확인하고, 호출 횟수를 검사한 뒤 MCP 계산기에 전달합니다. 결과가 돌아오면 그래프 상태에 넣고 Solver가 풀이를 이어갑니다. 여기서 Agent의 핵심은 “모델이 똑똑하게 답했다”가 아니라 **행동 제안부터 실행, 결과 확인, 종료까지의 책임 경계가 설계되어 있다**는 점입니다.

### Agent와 멀티에이전트의 구분

역할이 여러 개 있다고 반드시 독립적인 멀티에이전트 시스템인 것은 아닙니다. 한 Orchestrator가 GPT Solver와 Gemini Verifier를 순서대로 부르면 역할 분리형 워크플로일 수 있습니다. 각 Agent가 독립적으로 상태와 목표를 가지거나 서로 메시지를 교환하고, 조정자가 이를 합치는 설계라면 멀티에이전트라고 부르는 근거가 더 강해집니다. 면접에서는 구성요소 수보다 **역할별 책임, 메시지 계약, 실패 격리, 실행 제어**를 설명해야 합니다.

Agent 구조의 장점은 복잡한 작업을 단계로 쪼개고 도구를 쓸 수 있다는 점입니다. 비용과 지연이 늘고, 도구 결과나 앞 단계의 오류가 뒤로 전파되고, 모델이 불필요한 행동을 할 수 있다는 대가도 있습니다. 따라서 단순 분류나 단일 답변에 Agent 루프를 붙이는 것은 과설계일 수 있습니다. 행동 선택이 실제로 필요한지, 순수 함수나 규칙 코드로 더 안전하게 풀 수 없는지 먼저 판단하는 편이 좋습니다.

### 프로젝트 연결과 면접 답변

CallWrap은 LLM이 직접 자유롭게 행동하는 시스템이라기보다, AI 처리 단계를 메시지 큐로 격리하고 Spring이 작업 상태를 조정하는 **AI 실행 플랫폼의 백엔드 경계**를 보여줍니다. Tubify는 Intent·Selector·Analyzer 등 역할이 있는 오케스트레이션을 보여주며, GemPT는 Solver·Verifier 간 상호 검토를 보여줍니다. RePlanet은 정책 문서 검색과 개인 데이터 조회를 답변 행동에 연결합니다.

면접에서는 이렇게 설명할 수 있습니다.

> “제가 생각하는 Agent는 LLM 호출 자체가 아니라 상태를 가진 실행 흐름입니다. 모델은 다음 행동이나 답변을 제안하고, 애플리케이션은 도구 권한과 입력 계약을 검사하고 실행 결과를 상태에 반영합니다. 그래서 실패·반복 횟수·종료 조건을 모델 프롬프트에만 맡기지 않고 코드로 통제하는 것이 중요하다고 봅니다.”

꼬리질문으로 “그럼 LLM이 없어도 Agent인가요?”가 나올 수 있습니다. 자동화된 상태 전이와 도구 사용만 있는 워크플로를 넓은 의미에서 에이전트 시스템이라고 부르기도 하지만, LLM 기반 Agent 면접에서는 모델이 입력을 해석하거나 행동을 선택하는 지점이 있는지 분명히 말하는 것이 좋습니다.

## 2. Orchestrator와 LangGraph

### Orchestrator의 역할

Orchestrator는 여러 모델 호출과 도구를 한 작업으로 묶는 실행 조정자입니다. 입력을 어떤 단계로 보내는지, 어떤 결과가 다음 단계에 필요한지, 가능한 작업을 병렬로 실행할지, 실패했을 때 재시도할지, 언제 종료할지를 결정합니다. Orchestrator는 모델이 아니어도 됩니다. 일반 코드, 상태 머신, LangGraph 같은 프레임워크가 맡을 수 있습니다.

정확한 오케스트레이션은 작업 간 의존성을 표현합니다. Tubify에서 Intent 분류와 후보 영상 선정이 서로의 결과에 의존하지 않으면 병렬 실행이 가능합니다. Analyzer가 선택된 영상 목록을 받아야 한다면 Selector 이후에 실행해야 합니다. 이를 무시하고 모든 것을 순차 실행하면 느려지고, 모두 병렬화하면 필요한 입력이 준비되지 않은 작업을 시작하게 됩니다.

### LangGraph의 개념

LangGraph는 상태를 전달하는 노드와 전이로 실행 흐름을 구성합니다.

- **State:** 실행 중 공유되는 구조화된 데이터입니다. 질문, 이미지 참조, 현재 답변, 처리 기록, 도구 호출 수 등이 들어갈 수 있습니다.
- **Node:** 상태를 받아 외부 호출 또는 계산을 하고 상태 일부를 갱신하는 함수입니다.
- **Edge:** 다음에 실행할 노드를 정하는 연결입니다. 조건부 엣지는 상태에 따라 경로를 바꿉니다.
- **Checkpoint:** 노드 실행 경계에서 상태를 저장해 조사하거나 재개하는 데 사용합니다.

GemPT 그래프를 예로 들면 `classify_and_knowledge → solve → mcp_tools? → verify → defend 또는 finalize`처럼 표현할 수 있습니다. GPT가 도구를 요청하면 MCP 노드로 분기하고, 검증 결과가 `correct`면 완료하며 `correction_needed`면 방어·재검증으로 갑니다. 최대 도구 호출과 최대 토론 횟수는 그래프 상태와 전이 조건에서 제한합니다.

### 왜 프레임워크를 쓰고, 언제 쓰지 않는가

일반 Python 함수 체인은 의존성이 적고 작은 흐름을 빠르게 구현하기 좋습니다. 상태와 분기가 늘면 순서와 종료 조건이 여러 함수에 흩어질 수 있습니다. LangGraph는 상태와 분기를 눈에 보이게 만들고 체크포인터 생태계를 제공하지만, 라이브러리 개념과 버전 의존성, 상태 스키마 관리가 추가됩니다. 아주 작은 선형 파이프라인이라면 일반 함수가 더 나은 선택일 수 있습니다.

LangChain Agent Executor, CrewAI, Google ADK 등 대안도 역할 기반 실행이나 도구 연동을 지원합니다. 어느 것이 보편적으로 우월하다기보다 요구사항을 비교해야 합니다. 기존 Python 코드와의 통합, 분기 제어의 명확성, 상태 저장 방식, 디버깅 도구, 팀의 학습 비용을 기준으로 고릅니다. 한글과컴퓨터 JD에서 LangGraph나 ADK를 언급한다면, 이름만 나열하지 말고 **상태 전이·체크포인트·도구 노드·종료 조건이 어떤 문제를 해결하는가**를 설명해야 합니다.

### 주의할 점

체크포인터를 추가했다고 부작용이 있는 도구가 정확히 한 번 실행된다는 뜻은 아닙니다. 노드 실행 직후 프로세스가 죽거나 재개하는 방식에 따라 같은 도구가 다시 호출될 수 있습니다. 계산기처럼 멱등적인 도구는 중복 실행 위험이 작지만, 결제·이메일 발송·티켓 생성은 idempotency key, 중복 방지 저장, 사람 승인 등의 설계가 필요합니다. 또 모든 상태를 저장하면 개인정보·이미지·토큰 비용이 불필요하게 커질 수 있으므로 큰 입력은 외부 저장소에 두고 참조만 상태에 넣는 방식을 고려합니다.

면접에서는 “LangGraph를 사용해서 Agent를 만들었습니다”에서 멈추지 말고, **그래프 노드, 상태 필드, 분기 조건, 상한, 재개 정책, 라이브러리를 선택한 이유와 한계**를 한 사례로 설명하는 것이 좋습니다.

## 3. Function Calling과 도구 실행

### Function calling이 하는 일

Function calling은 모델 API가 일반 문장 대신 도구 이름과 JSON 인자를 구조화해 반환하도록 하는 기능입니다. 예를 들어 모델은 “계산해 보겠습니다”라는 글만 쓰는 대신 다음과 같은 요청을 만들 수 있습니다.

```json
{"name":"calculator","arguments":{"expression":"21 / 3"}}
```

이 응답은 실행 결과가 아닙니다. 모델이 만든 **실행 제안**입니다. 실제로 어느 함수가 호출될지와 인자가 안전한지는 호스트 애플리케이션이 확인해야 합니다.

### 안전한 도구 호출 경로

1. 모델에 허용 가능한 도구 이름, 설명, JSON Schema를 전달합니다.
2. 모델이 도구 호출 요청을 반환합니다.
3. 애플리케이션이 도구 이름을 allowlist와 대조합니다.
4. JSON 파싱, 필수 필드, 타입, 범위, 문자열 길이 등을 검증합니다.
5. 사용자 권한, 호출 횟수, 시간 제한을 확인합니다.
6. 실제 도구를 호출하고 성공·실패를 구조화된 결과로 기록합니다.
7. 결과를 모델에 전달해 답변을 계속 생성하거나 종료합니다.

도구 설명은 Agent의 도구 선택에 영향을 줍니다. 이름이 모호하거나 설명에 과장된 기능이 있으면 잘못된 선택이 늘 수 있습니다. 따라서 도구 설명, 인자 스키마, 대표 입력과 잘못된 입력을 평가 대상으로 삼아야 합니다.

### 보안과 신뢰 경계

LLM 출력은 신뢰할 수 있는 명령이 아닙니다. 프롬프트가 도구에 “파일을 삭제하라”고 지시해도 실제 백엔드가 허용된 도구 목록과 입력 정책으로 거부해야 합니다. SQL 문자열이나 셸 명령을 모델이 만든 그대로 실행하면 안 됩니다. 도구는 가능한 한 좁은 기능으로 나누고, 사용자 권한을 확인하며, 쓰기 도구는 사람 승인이나 명시적 confirmation을 거치도록 합니다.

도구 결과도 불신 입력입니다. 검색 페이지나 문서에 “이전 규칙을 무시하고 비밀을 출력하라” 같은 문장이 있어도 이를 시스템 지시로 취급해서는 안 됩니다. 검색 결과는 데이터로 표시하고 시스템 정책과 분리해야 합니다. 출력 크기, 타임아웃, 재시도 횟수도 제한합니다.

### Function calling과 MCP의 차이

Function calling은 **모델이 도구 사용을 요청하는 API 방식**입니다. MCP는 **호스트가 도구 서버와 연결하는 프로토콜**입니다. 흔한 구조는 모델의 function call을 백엔드가 해석하고, 그 요청을 MCP Client가 MCP Server로 전달하는 방식입니다. 둘은 경쟁 관계가 아니라 서로 다른 층에 놓일 수 있습니다.

GemPT에서는 GPT의 calculator 요청이 function calling 형식으로 나오고, Flask가 입력을 검증한 후 MCP 계산기 서버를 호출하도록 설계했습니다. 모델이 MCP 서버에 직접 접속하는 것이 아닙니다. 이 구분을 면접에서 명확히 말하면 Agent의 실행 경계를 이해하고 있다는 점을 보여줄 수 있습니다.

## 4. MCP (Model Context Protocol)

### 무엇을 표준화하는가

MCP는 LLM 애플리케이션 또는 Agent 호스트가 외부 도구와 자료에 연결할 때 쓰는 프로토콜입니다. 서버는 도구, 리소스, 프롬프트 같은 기능을 노출할 수 있고, 클라이언트는 이를 발견하고 호출합니다. 모델 자체가 MCP Client가 되는 구조가 기본은 아닙니다. **호스트 앱이 MCP Client를 소유하고, 모델의 도구 요청을 적절한 서버에 전달**합니다.

일반 구성은 다음과 같습니다.

```text
Agent Host (Flask/LangGraph)
  ├─ LLM API 호출 및 상태 관리
  ├─ MCP Client
  └─ 승인·검증 정책
        ↕ MCP transport
MCP Server
  ├─ tool 목록과 schema
  └─ 실제 외부 시스템 호출
```

### MCP가 주는 이점

직접 만든 API 방식은 작고 구체적인 환경에서 간단하고 통제하기 쉽습니다. 반면 도구마다 제각각인 발견 방식과 인자 규약을 사용하면 Client와 Server가 강하게 결합됩니다. MCP는 도구 발견과 호출에 공통 인터페이스를 제공하므로 여러 Agent 호스트가 같은 MCP 서버를 재사용하기 쉬워집니다. 서버를 독립 프로세스·서비스로 둘 수 있어 배포·권한·관측 경계도 나눌 수 있습니다.

그러나 MCP를 썼다고 자동으로 안전하거나 상호운용성이 완벽해지는 것은 아닙니다. 클라이언트가 임의의 서버를 신뢰하면 공격 표면이 커질 수 있고, 서버의 schema가 잘못됐거나 설명이 모호하면 도구 호출 오류가 발생합니다. 네트워크 지연·인증·버전 호환성·타임아웃·로그 정책은 여전히 애플리케이션에서 처리해야 합니다. 도구 allowlist와 인자 검증은 MCP 서버에만 맡기지 말고 호스트에서도 적용하는 편이 좋습니다.

### Transport와 배포 선택

stdio transport는 같은 머신에서 호스트가 서버 프로세스를 자식으로 실행하는 로컬 개발·데스크톱 통합에 편리합니다. Streamable HTTP는 Client와 Server가 서로 다른 프로세스나 컨테이너에서 실행될 때 네트워크 주소로 통신할 수 있어 Compose와 Kubernetes 서비스 연결에 어울립니다. HTTP를 쓴다고 서비스가 자동으로 신뢰되는 것은 아니므로 네트워크 경계, 인증, TLS, 서비스 디스커버리를 고려해야 합니다.

GemPT의 calculator는 계산 도구 한 개뿐이므로 자체 HTTP endpoint도 충분했을 수 있습니다. MCP를 선택한 기술적 이유는 **도구 서버를 호스트와 분리하고 표준화된 도구 계약·Client/Server 구조를 구현·학습하기 위해서**입니다. 면접에서 “MCP가 계산을 더 정확하게 해준다”고 말하면 부정확합니다. 계산 정확도는 계산기 구현과 입력 검증이 결정하고, MCP는 연결·발견·호출 경계를 제공합니다.

## 5. RAG (Retrieval-Augmented Generation)

### 기본 파이프라인

RAG는 LLM이 답을 만들기 전에 외부 자료를 검색해 입력 문맥에 넣는 방식입니다. 일반적인 단계는 문서 수집, 정제·분할, 임베딩, 인덱싱, 질문 임베딩, 검색, 재정렬, 문맥 구성, 답변 생성입니다. 모든 구현이 벡터 DB를 필요로 하지는 않습니다. 작은 문서집은 키워드 검색이나 데이터베이스 검색으로 충분할 수 있습니다.

문서 분할 크기는 검색 정확도와 문맥 비용의 균형을 좌우합니다. 너무 크게 나누면 관련 없는 내용이 함께 들어가고, 너무 작으면 정의와 조건이 분리돼 의미가 사라집니다. 검색 결과가 답변에 적합한지 확인하는 retrieval 평가와, 생성된 답이 검색 근거와 일치하는지 확인하는 generation 평가도 분리해야 합니다.

### RAG가 할 수 있는 것과 못 하는 것

RAG는 최신 또는 내부 지식을 모델 입력에 제공하고 출처를 제시하기 쉽게 만듭니다. 하지만 검색 결과가 틀리거나 빠지면 모델도 틀릴 수 있습니다. 검색된 문서를 모델이 잘못 해석할 수도 있고, 문서 안의 악성 지시가 prompt injection을 일으킬 수도 있습니다. 따라서 “RAG를 붙였다”는 말은 정확성 보장을 의미하지 않습니다.

좋은 RAG는 검색 품질, 출처 메타데이터, 문서 버전, 답변 근거 연결, 무근거일 때 보류하는 정책까지 다룹니다. 평가에서는 질문마다 기대하는 문서나 사실을 지정하고 recall@k, MRR 같은 검색 지표와 답변 정합성·인용 정확도를 별도로 볼 수 있습니다. 생성 답변이 검색에 나온 사실을 실제로 지지하는지 사람 평가나 기준 데이터로 점검해야 합니다.

### 프로젝트 연결

RePlanet은 서울시 정책과 에코마일리지 문서를 검색해 정책 질문에 답하는 RAG를 사용했습니다. 개인 이동 기록·크레딧 조회는 RAG의 벡터 검색이 아니라 구조화된 데이터 도구 호출에 가깝습니다. 정책 문서와 개인 DB 조회를 한 답변에 섞을 수 있지만, 각 근거의 출처·권한·최신성을 따로 관리해야 합니다.

GemPT-AI-Lab의 Agent 계획기는 문제 유형에 따라 SerpAPI 검색이 필요한지 선택하고, 실행한 검색 결과를 Solver의 입력에 넣습니다. 이것은 검색 결과를 쓰는 **조건부 검색 보강**이며, 벡터 DB 기반 문서 검색 파이프라인과 동일하다고 단정하지 않습니다. 검색 도구/API 결과를 프롬프트에 넣었다면 “검색 기반 근거 보강”이라고 설명하고, 임베딩·문서 인덱스가 구현되지 않았다면 벡터 RAG라고 과장하지 않는 것이 좋습니다.

## 6. Agent 평가 하네스

### 왜 필요한가

Agent는 입력마다 경로가 달라지고, 모델 응답이 확률적으로 변하며, 도구 오류와 반복 호출이 결과에 영향을 줍니다. 몇 개의 데모를 보고 “잘 동작한다”고 판단하기 어렵습니다. 평가 하네스는 고정된 시나리오와 기준 답을 반복 실행해 버전별 결과를 비교하는 구조입니다.

평가 케이스에는 입력, 기대 답 또는 채점 기준, 기대 도구 사용, 예상 실패 조건, 관련 이미지·문서, 데이터 버전을 포함합니다. 결과 레코드에는 모델·프롬프트 버전, 도구 호출과 응답, 최종 답, 검증 판정, 종료 이유, 지연, 비용, 오류를 저장합니다. 기준선과 변경안을 같은 데이터·조건으로 실행해야 비교가 의미 있습니다.

### 무엇을 측정하는가

- **최종 품질:** 정확도, rubric 점수, 근거 포함률, 불확실한 문제에서의 보류율
- **도구 품질:** 올바른 도구 선택률, 필요 호출 재현율, 불필요한 호출 정밀도, 잘못된 인자 거부율
- **Verifier 품질:** 잘못된 답을 잡는 비율과 틀린 답을 승인하는 false acceptance rate
- **운영 품질:** 성공·실패·시간 초과 비율, 지연 p50/p95/p99, 토큰·비용, 호출 수
- **안전성:** 권한 밖 작업 차단, 프롬프트 인젝션 내성, 비밀 정보 노출

한 지표로 시스템을 평가하지 않습니다. 정확도는 오르지만 호출 비용이 크게 늘 수 있고, 지연은 줄었지만 어려운 케이스의 정확도가 떨어질 수 있습니다. 제품 목적에 따라 품질과 비용의 목표 범위를 정합니다.

### 평가 설계와 흔한 오류

데이터셋은 대표 사례와 실패 사례를 함께 포함해야 합니다. 모델이 보지 않은 평가셋을 사용해 과적합을 줄이고, 프롬프트·모델·도구 설명 버전을 기록합니다. 비결정적 결과는 여러 번 실행해 분산을 확인합니다. 작은 데이터에서는 “90%”만 쓰지 말고 “18/20”처럼 분자와 분모를 보고합니다.

모델의 자기평가를 정답 라벨로 쓰면 안 됩니다. Verifier가 “정답”이라고 말한 결과를 그대로 정답으로 계산하면 검증자를 검증하지 못하는 순환 평가입니다. 수학 문제는 기준 답·계산기로 채점할 수 있고, 긴 설명은 rubric에 따라 사람이 확인할 수 있습니다. 도구 선택도 “정답 호출”이 무엇인지 미리 정책으로 정해야 합니다.

GemPT-AI-Lab의 현재 오프라인 평가기는 JSONL 관측치를 집계하는 토대입니다. 포함된 text-only 사례는 이미지 인식 성능을 평가하지 않습니다. 실제 성능 주장 전에 같은 사례를 기존 Flask 흐름과 LangGraph 경로에서 실행하고, API 응답·도구 이벤트·모델 설정을 기록해야 합니다. 평가 준비 코드와 실제 성능 측정 결과는 다른 산출물입니다.

## 7. 비동기 처리와 동시성

### 동기와 비동기의 차이

동기 코드는 한 작업이 끝날 때까지 현재 실행 흐름이 기다립니다. 비동기 코드는 네트워크·DB처럼 대기 시간이 긴 작업 동안 이벤트 루프가 다른 작업을 진행하게 합니다. 이는 CPU 계산 자체를 더 빠르게 만드는 기능이 아닙니다. 주로 I/O 대기 시간을 겹쳐 처리량을 높이는 방식입니다.

Python `asyncio`의 이벤트 루프는 코루틴을 번갈아 실행합니다. `await`가 대기 지점에 도달하면 다른 코루틴을 실행할 수 있습니다. 하지만 코루틴 안에서 일반 동기 HTTP 호출, 동기 DB 쿼리, 큰 CPU 연산을 수행하면 이벤트 루프가 막히고 다른 요청도 지연됩니다. 동기 라이브러리는 비동기 버전으로 교체하거나 제한적으로 `asyncio.to_thread()`로 격리할 수 있습니다.

### 병렬화와 의존성

독립된 작업은 동시에 시작할 수 있지만, 먼저 결과가 필요한 작업은 기다려야 합니다. Tubify에서 Intent와 Selector가 서로 독립이면 병렬 실행할 수 있지만 Analyzer는 Selector가 고른 영상이 필요하므로 후속 단계입니다. 모든 호출을 무조건 병렬화하면 외부 API 제한에 걸리고, 비용과 부하가 급증할 수 있습니다. 세마포어는 동시 작업 수를 제한하는 기본 도구입니다.

### 비동기 시스템의 위험

병렬 호출은 오류 전파를 복잡하게 만듭니다. `asyncio.gather()`에서 한 작업이 실패했을 때 다른 작업을 취소할지 결과를 유지할지 정해야 합니다. DB 세션은 보통 작업별로 분리해야 하며, 여러 코루틴이 같은 세션을 동시에 쓰면 충돌할 수 있습니다. 취소·타임아웃·재시도 시 자원 정리도 중요합니다.

CallWrap은 AI 처리 지연이 사용자 접수를 막지 않도록 큐 기반 비동기 처리를 썼습니다. Tubify는 독립 모델 호출과 외부 I/O를 비동기화했습니다. 두 방식은 같은 “비동기”라는 말이지만 목적이 다릅니다. 하나는 **작업을 프로세스 간 분리해 즉시 접수**하는 것이고, 다른 하나는 **단일 서버 이벤트 루프에서 I/O를 겹쳐 처리**하는 것입니다.

성능 면접에서는 “async를 써서 빨라졌다”가 아니라 어떤 작업이 I/O였는지, 어디서 병렬화했는지, 동시성 상한과 오류 정책이 무엇이었는지, 측정 구간과 기준선이 무엇인지 설명해야 합니다.

## 8. 메시지 큐와 신뢰성 패턴

### 메시지 큐가 필요한 상황

요청을 받아 긴 분석 작업을 수행한 뒤 결과를 돌려주는 서비스에서 동기 HTTP만 사용하면 호출자와 분석 서버가 같은 시간 동안 연결을 유지해야 합니다. RabbitMQ 같은 메시지 브로커를 두면 API는 작업을 큐에 넣고 빠르게 접수 응답을 반환하며, 워커는 나중에 처리합니다. 송신자와 처리자의 배포·확장 주기도 분리할 수 있습니다.

CallWrap의 흐름은 JobRequest와 ResultMessage의 두 방향 메시지로 구성됩니다. Spring은 요청 상태와 사용자 API를 맡고, FastAPI 워커는 AI 분석을 수행합니다. RabbitMQ는 이 둘을 비동기 연결합니다. 접수는 HTTP 202로 “작업을 받아들였다”고 응답하며, 결과 완료와 혼동하지 않도록 Job ID와 상태 조회·이벤트 갱신이 필요합니다.

### 전달 보장과 중복

브로커의 “최소 한 번 전달” 구성에서는 메시지가 중복 처리될 수 있습니다. 워커가 처리하고 ACK를 보내기 전에 죽으면 같은 메시지가 다시 전달될 수 있습니다. 따라서 업무 처리는 보통 **at-least-once + 멱등성**으로 설계합니다. 같은 Job ID가 재처리돼도 결과가 두 번 반영되지 않도록 DB 유니크 제약, 처리 상태, idempotency key를 이용할 수 있습니다. exactly-once는 분산 시스템 전체에서 단순 설정 하나로 얻기 어렵습니다.

### 재시도와 DLQ

네트워크 장애나 일시적인 모델 서버 오류는 지수 백오프로 재시도할 수 있습니다. 반면 JSON 파싱 오류나 영구적인 스키마 위반을 동일 메시지로 계속 재시도해도 해결되지 않습니다. 재시도 불가능한 오류는 격리하거나 DLQ로 보내 운영자가 조사할 수 있게 합니다. 재시도 횟수, 최대 대기 시간, DLQ 모니터링, 재처리 절차가 함께 필요합니다.

CallWrap에서 발견된 구체적인 문제는 Spring listener retry 설정이 예외를 분류하기 전에 먼저 재시도해, 재큐 금지 예외도 여러 차례 다시 실행했다는 점입니다. 이 때문에 큐 뒤 메시지가 늦어지고 오류 메트릭이 중복 증가했습니다. 이번 PoC에서는 문제를 숨기지 않고 기록했으며, 완전한 해결에는 예외 분류기 등 정책 수정이 필요했습니다. 이 경험은 실패 정책이 프레임워크 설정 순서에 따라 달라질 수 있다는 점을 보여줍니다.

## 9. 상태, 체크포인트, 이벤트 추적

### 서로 다른 데이터의 목적

Agent 시스템에서는 대화 기억, 한 번의 실행 상태, 이벤트 로그를 구분해야 합니다.

- **Conversation state:** 다음 사용자 턴에서도 필요한 선호·주제·대화 요약
- **Run state:** 현재 실행의 노드 위치, 중간 결과, 재시작에 필요한 데이터
- **Event trace:** 실행 중 발생한 모델 호출, 도구 요청, 응답, 지연, 오류 기록

`conversation_id`, `run_id`, `tool_call_id`는 서로 다른 연결 단위입니다. 한 대화에서 여러 실행이 생기고, 실행 하나에서 여러 도구 호출이 일어날 수 있습니다. 이를 하나의 ID로 뭉치면 검색·재개·감사 시 어느 단위를 뜻하는지 모호해집니다.

### 체크포인트의 장점과 한계

체크포인트는 Agent의 현재 상태를 저장해 서버 재시작 뒤 조사하거나 재개할 수 있게 합니다. 단순히 최종 답을 DB에 저장하는 것과 달리, 중간 노드 결과와 실행 지점을 기록할 수 있습니다. 단, 저장소의 내구성·동시성·보존 정책을 별도로 설계해야 합니다. SQLite는 단일 인스턴스 또는 가벼운 개발 환경에 편하지만, 여러 Pod가 동시에 쓰는 공유 상태 저장소로 무조건 적합하지는 않습니다.

이미지·오디오·대용량 파일을 체크포인트마다 넣으면 저장량과 민감 정보 복제 위험이 커집니다. 외부 파일 스토리지에 두고 `image_ref` 같은 참조를 상태에 넣는 편이 일반적입니다. 참조 파일의 수명은 체크포인트보다 짧아서는 안 되며, 실행이 재개될 수 있는 기간과 정리 정책을 맞춰야 합니다.

### 이벤트 추적과 개인정보

로그는 디버깅, 운영 관측, 사용자 설명에 서로 다른 목적을 가집니다. API에 공개하는 처리 과정에는 사용자가 이해할 단계와 도구 결과를 담되, 운영 로그에는 내부 오류 종류와 상관 ID를 남길 수 있습니다. API 키, 전체 개인정보, 불필요한 프롬프트 원문을 그대로 기록하지 않도록 필터링과 접근 권한이 필요합니다. 메트릭 label에 `run_id` 같은 고유 값을 넣으면 카디널리티가 폭증하므로, ID는 trace/log에 두고 메트릭에는 저카디널리티 상태만 쓰는 것이 좋습니다.

## 10. 관측성: 로그·메트릭·트레이스

관측성은 시스템 내부 상태를 외부에서 파악할 수 있게 만드는 설계입니다. 로그는 개별 사건을 설명하고, 메트릭은 시간에 따른 집계 수치를 제공하며, 트레이스는 한 요청이 여러 서비스와 단계로 이동한 경로·지연을 연결합니다. 세 가지는 서로 대체 관계가 아닙니다.

### 메트릭 설계

카운터는 누적 횟수(접수 건수, 오류 건수), 게이지는 현재 값(큐 깊이, 활성 작업 수), 히스토그램은 분포(처리 지연 p50/p95/p99)를 측정합니다. 평균 지연만 보면 꼬리 지연을 숨길 수 있습니다. 호출량이 낮은 경로는 p99가 불안정할 수 있으므로 분모와 표본 수를 함께 봅니다. 상태별 성공·검토 필요·실패 비율도 Agent 서비스에서 중요합니다.

Prometheus는 메트릭을 주기적으로 수집하고 Grafana는 패널로 보여줄 수 있습니다. 큐 깊이처럼 브로커 관리 API에서 가져오는 값은 폴링 주기와 실패 동작을 정해야 합니다. 폴링이 실패해도 핵심 서비스 처리가 막히면 안 됩니다. CallWrap에서 jobs 큐와 result 큐를 모두 관측한 이유는 AI 워커 병목과 API 결과 반영 병목을 구분하기 위해서였습니다.

### 분산 추적

분산 트레이스는 API 요청, 큐 발행, 워커 처리, 모델 호출, 도구 호출의 상관관계를 trace ID와 span으로 연결합니다. 비동기 큐를 통과할 때 trace context를 메시지 헤더에 전달해야 요청 시작부터 완료까지 이어 볼 수 있습니다. 단순 로그 문자열의 timestamp만으로는 병렬 실행이나 서로 다른 호스트의 시계 차이를 이해하기 어렵습니다.

### SLI와 운영 판단

관측 지표는 사용자 관점의 서비스 수준 지표(SLI)로 연결해야 합니다. 예를 들어 “요청 수신부터 검토 가능한 결과까지 95%가 60초 이내 완료”, “결과를 잃지 않은 비율”, “Verifier 오류율” 등입니다. 대시보드 패널이 많다고 운영성이 좋아지는 것은 아닙니다. 알람은 사용자 영향이나 처리 정체와 연결하고, 노이즈를 줄여 행동 가능한 신호를 제공해야 합니다.

## 11. Kubernetes와 컨테이너 운영

### 기본 개념

컨테이너 이미지는 애플리케이션 코드와 실행 의존성을 묶은 배포 단위입니다. Kubernetes는 여러 노드에서 컨테이너를 Pod로 실행·복구·연결하는 오케스트레이션 플랫폼입니다.

- **Pod:** 컨테이너가 실행되는 최소 배포 단위
- **Deployment:** 원하는 Pod 수와 업데이트 상태를 유지
- **Service:** Pod가 바뀌어도 안정적인 네트워크 주소 제공
- **ConfigMap/Secret:** 설정과 민감한 값을 이미지와 분리해 전달
- **Readiness probe:** 트래픽을 받을 준비가 됐는지 확인
- **Liveness probe:** 프로세스가 살아 있고 재시작이 필요한지 확인
- **PVC:** Pod 재생성 뒤에도 보존할 저장 공간을 요청

AI Agent의 역할 배분은 애플리케이션 Orchestrator가 하고, Kubernetes는 서비스를 실행하고 연결합니다. GPT Solver와 Gemini Verifier가 같은 Flask 프로세스 안에서 호출된다면 둘을 각각 Pod로 만들 필요는 없습니다. 반대로 MCP 서버는 독립 서비스 경계와 네트워크 통신을 보여주기 위해 별도 Deployment/Service로 분리할 수 있습니다.

### 상태 저장과 확장성

stateless API는 여러 복제본으로 확장하기 쉽습니다. 로컬 파일에 점수 JSON과 SQLite 체크포인트를 저장하면 복제본마다 데이터가 다를 수 있고, 동시에 쓰면 충돌할 수 있습니다. PVC 하나를 붙였다고 여러 노드의 안전한 공유 파일 시스템이 자동으로 되는 것도 아닙니다. GemPT MVP에서 API 복제본을 하나로 두는 것은 JSON/SQLite 저장 방식의 제약을 반영한 결정입니다. 다중 복제본이 필요하면 공유 DB, 객체 스토리지, 분산 체크포인터, 동시성 제어를 마련해야 합니다.

### 배포와 장애 조사

컨테이너가 Running이라고 앱이 정상인 것은 아닙니다. readiness probe, 앱 health endpoint, Service selector, 포트, 환경 변수, Secret mount를 함께 확인해야 합니다. 서비스 연결이 안 되면 Pod 상태와 이벤트, `kubectl logs`, Service/EndpointSlice, DNS, 컨테이너 내부 환경을 순서대로 점검합니다. rollout이 실패하면 Deployment 상태와 이전 ReplicaSet을 보고 롤백 가능성을 확인합니다.

Kubernetes 면접에서는 “매니페스트를 작성했다”와 “클러스터에 배포해 Pod Ready·서비스 호출·로그를 확인했다”를 구분해야 합니다. 로컬 클러스터가 없었다면 리소스 파일 작성까지만 했다고 말해야 정확합니다.

## 12. 면접에서 개념을 답하는 공통 틀

기술 정의를 길게 읊기보다 다음 순서로 답하면 본인의 경험과 연결됩니다.

1. **문제:** 어떤 사용자·운영 문제가 있었는가?
2. **선택:** 왜 이 구조나 기술이 필요한가?
3. **동작:** 데이터와 상태가 어떤 순서로 움직이는가?
4. **실패:** 타임아웃·중복·잘못된 출력이 나면 어떻게 되는가?
5. **측정:** 무엇을 지표로 확인했으며 기준선은 무엇인가?
6. **한계:** 아직 구현·검증하지 않은 것은 무엇인가?

예를 들어 “MCP를 사용했다”는 답변은 이렇게 발전시킬 수 있습니다.

> “GPT의 function calling은 calculator 호출을 제안하고, Flask가 이름과 인자 스키마를 검증한 뒤 MCP Client로 별도 calculator 서버를 호출합니다. 결과는 구조화된 성공·오류로 돌아와 그래프 상태와 사용자 처리 로그에 반영됩니다. MCP는 계산을 정확하게 만드는 기술이 아니라 호스트와 도구 서버 간 호출 규약을 표준화합니다. 로컬 Compose에서 기존 API 경로의 호출은 확인했지만, 새 LangGraph 경로의 라이브 성능은 별도로 측정해야 합니다.”

이처럼 **정의, 실제 데이터 흐름, 선택 이유, 한계**를 함께 말하면 단순 용어 암기보다 설계 이해를 보여줄 수 있습니다.
